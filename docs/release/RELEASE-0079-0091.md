### 2a. Rehearsal on the hosted Postgres build (Supabase Postgres 17.6.1.166)

Repeated on the image hosted runs (`supabase/postgres:17.6.1.166`, the same build string as the hosted
project) with `scripts/release/rehearse-supabase17.sh`. Migrations were applied as `postgres` (not a
superuser, as on hosted, under `supautils`); the API reached the database through the image's own
`authenticator` role (with `safeupdate` and its statement/lock timeouts).

What the Postgres 16 rehearsal could not show, and this one does: the `MAINTAIN` table privilege
(new in 17, which 0201 checks); applying as the non-superuser `postgres` under `supautils` rather than as
a superuser; `safeupdate` (rejects an `UPDATE`/`DELETE` without `WHERE`) and the statement/lock
timeouts on the API's connection role; and the hosted build's planner and catalogue.

|---|---|
| Apply 0079 → 0091 to the populated 0078 database (4,016 rows) | all 13 applied, 59–104 ms each |
| Data preserved (`snapshot.sql`) | every existing table identical; `component_definitions` 9 → 35, original 9 identical |
| Isolation sweep on populated data | **0 leaks** across 103 tables |
| pgTAP on 0078 + seed upgraded to 0091, run as `postgres` | **1,261 of 1,261 passed** |

What the rehearsal had to add, because the bare image is not a configured project
(`scripts/release/supabase17-services.sql`; none of it is in a migration):

- **The auth and storage services' tables and helpers** (`auth.users` columns, `auth.identities`,
  `storage.buckets/objects`, the current `auth.uid()`/`auth.jwt()` reading `request.jwt.claims`). The
  hosted project has the real services.
- **Two hosted dashboard settings, read from the hosted catalogue (read-only):** default privileges for
  objects `postgres` creates in `public` (functions to `postgres` only; sequences to `postgres` and
  `service_role` read/usage), and the "automatic RLS" event trigger `ensure_rls` → `public.rls_auto_enable()`.
  Without them the image grants `anon` EXECUTE on every new function, and three pgTAP checks
  (0201, 0300 allowlist, 0317) correctly fail. **This is a property of the hosted configuration the
  migrations rely on, not of the migrations: if those settings were ever changed on hosted, the
  tests in 0201/0300/0305 are what would catch it.**
- pgTAP installed in `public` (where the suite looks for it; hosted has it in `extensions`, and the
  suite is never run against hosted).

**Differences that remain:** the rehearsal used the real hosted Postgres build, but the auth/storage
services were stand-ins and the data was the fixture, not production's. The remaining way to close
that gap is a Supabase branch of production (step 3 below), which also exercises `supabase db push`
and the migration history table.

## 3. Deployment sequence

Order matters in one direction only: **database first, then the API, then the web app.** The 0078-era
API works on the 0091 schema (tested); the new API needs 0091.

1. **Approval.** The owner approves this release in writing.
2. **Freeze and checkpoint.** Note the time for point-in-time recovery (Supabase PITR, or take a
   `pg_dump -Fc` of the database). Pause the workers (`apps/workers`) so no job runs mid-migration.
3. **Recommended: rehearse on a Supabase branch.** The 17.6 image rehearsal (§2a) has passed; a branch
   of production adds the real auth/storage services, production's own rows and the `supabase db push`
   path. Create the branch, run `scripts/release/snapshot.sql`, apply 0079–0091, run the snapshot
   again and `scripts/release/isolation-sweep.sql`, then delete the branch. (Billed while it exists.)
   If the owner declines it, re-run `rehearse-supabase17.sh` on the release commit instead.
4. **Apply migrations** 0079 → 0091 to production with the Supabase CLI (`supabase db push`) or one
   transaction per file, stopping on the first error. Expected total time: well under a second.
5. **Verify the database:** the history shows 0079–0091; `select count(*) from component_definitions
   where 'living' = any(allowed_spaces)` returns 26; the three new tables have RLS enabled
   (`select relrowsecurity from pg_class where relname in ('surface_preferences','work_handovers','renewal_proposals')`);
   run the isolation sweep against production as a read-only check if desired.
6. **Deploy the API** from the release commit (Render). Confirm `/health`; confirm the boot log line
   `AI gateway: provider=… configured=true` if model-assisted reading is wanted.
7. **Deploy the web app** (static build; only `VITE_PUBLIC_*` reaches the browser — checked by the build).
8. **Resume the workers.**
9. **Smoke test as a real member:** open Home, a renewal, a claim, a policy change and a client
   investigation; ask "what is blocking this?" in a claim; confirm a read-only member is offered no
   commands and is refused a claim write.

## 4. Recovery plan

Prefer fixing forward: every change is additive, and the application tolerates the old schema only in
the direction tested above.

- **The web or API release misbehaves, the database is fine:** redeploy the previous API and web
  builds. The 0078-era API runs correctly on the 0091 schema (188/188). Nothing else is needed.
- **A migration fails while applying:** each file is its own transaction, so a failed file leaves no
  partial change. Fix forward with a new migration, or stop; earlier files may stay (they are additive
  and the old API tolerates them).
- **The release must be withdrawn from the database:**
  1. Redeploy the previous API first. Restoring the 0085 functions re-opens the read-only write gap
     0085 closed; do not leave the new API running against them.
  2. Back up the release's own data:
     `pg_dump -a -t surface_preferences -t work_handovers -t renewal_proposals "$DATABASE_URL" > release-data.sql`.
  3. Run `scripts/release/rollback-0079-0091.sql` (one transaction).
  4. Verify the history no longer lists 0079–0091 and the three tables are gone.
  To re-release later: apply 0079–0091 again and load `release-data.sql`. Rehearsed end to end.
- **Anything worse:** restore to the checkpoint from step 2 (PITR or the dump). Everything written
  after the checkpoint is lost, so this is the last resort.
